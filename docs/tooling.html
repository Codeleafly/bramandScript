07 |   }

09 | }

11 | :done

Command Description

Diagnostics Engine

Zero-Box Clang/Rust-Style Diagnostic Engine

BramandScript employs a zero-box diagnostic formatter engineered for international terminal compatibility. Box-drawing characters (╭───╮, │, ╰───╯) commonly cause severe wrapping artifacts, broken vertical margins, and copy-paste corruptions on narrow mobile screens (Termux ARM64) and varied console emulators.

Our diagnostic engine replaces all box characters with clean, standard Clang/Rust-style vertical gutters (|), clickable file location links (--> file:line:col), 5-line contextual source windows, exact caret pointers (^), token span underlines (~~~), and actionable inline hints ([Hint: ...]):

terminal — zero-box compiler diagnostic 
✦ error[SyntaxError]: expected next token to be RPAREN, got INT instead
  --> server.bmd:14:28
   |
 9 |   let port = 8080
10 |   let host = "0.0.0.0"
11 |   
12 |   fn start_listener() {
13 |       println("Listening on", host, port)
14 |       if (connection_count > 100 200) {
   |                              ^~~ [Hint: check syntax for missing operator, parenthesis, or delimiter]
15 |           println("Server under load")
16 |       }
17 |   }
18 |   
19 |   start_listener()
   |

Diagnostic Architectural Principles

  • Clickable Hyperlinks (--> file:line:col): Formatted according to GNU/Rust convention, enabling direct click-to-open in VSCode, JetBrains, and modern terminal multiplexers.
  • 5-Line Source Window Context: Automatically loads up to 5 preceding and 5 succeeding lines surrounding the defect for instant situational context.
  • Exact Caret & Span Highlighting (^~~~): The caret points to the starting column, while tildes underline the token width.
  • Actionable Intelligence ([Hint: ...]): Every diagnostic is paired with heuristic rules that explain likely remedies directly in the terminal.

Standalone Compilation

Standalone Executable Compilation (bmd build)

Compile any BramandScript program into a completely self-contained, native executable. The generated binary contains the zero-dependency Bramand bytecode engine and an embedded virtual filesystem bundle (BMD_BUNDLE_V2), capable of running instantly on target systems without requiring Go or Bramand to be installed.

Single-Binary Embedding of Global Dependencies

When compiling a program with bmd build, the compiler recursively traverses all static and dynamic import statements across your project. It bundles not only local sibling source files, but also all resolved third-party packages from the centralized registry ($HOME/.bmd_libs/registry/) directly into the binary's compressed virtual filesystem.

bash — Standalone Single-Binary Builder 
# Build a standalone native binary bundling all dependencies
bmd build app.bmd -o my_app

# Build with Ahead-of-Time constant folding and opcode optimization
bmd build -O app.bmd -o my_app_optimized

# Execute standalone binary anywhere (no Go, no interpreter, zero dependencies!)
./my_app
Self-Contained Virtual Filesystem (embed:bundle/)

During standalone execution, the VM automatically intercepts imports matching bundled dependencies and resolves them transparently from the in-memory payload without requiring access to the host's $HOME/.bmd_libs/ directory or any active network connection.

Dependency & Package Architecture

Centralized Package Manager & Dependency Engine (bmd pkg)

BramandScript features a production-grade, centralized package management engine inspired by modern ecosystems like Go and Deno. Rather than littering disk storage with bloated, redundant per-project folders (node_modules/), all external modules, tarball archives, and versioned registries are stored in a single, system-wide centralized store at $HOME/.bmd_libs/.

Centralized Storage Hierarchy ($HOME/.bmd_libs/)

The centralized tree layout isolates immutable compressed tarballs, live unpacked registry packages, and cryptographic integrity locks:

Three-Tier Entrypoint Fallback Engine

When a package directory is imported without referencing an explicit subfile (e.g., import "github.com/alice/json-tools" as json), BramandScript's compiler executes the deterministic Three-Tier Fallback Engine:

Tier 1

Manifest Entry

Inspects bmdpkg.json. If "entry" is defined, resolves to specified file (e.g. src/index.bmd). If defined file is missing, aborts immediately with BrokenManifestError.

Tier 2

main.bmd Fallback

If no "entry" is set or manifest is absent, looks for main.bmd in the package root. If present, resolves as module entrypoint.

Tier 3

index.bmd Fallback

If main.bmd does not exist, looks for index.bmd. If none of the 3 candidates exist, compiler halts with a clean diagnostic error.

terminal — Diagnostic Output on Missing Entrypoint 
[ERROR] No entrypoint found: package must define bmdpkg.json, main.bmd, or index.bmd: /home/user/.bmd_libs/registry/github.com/alice/broken-pkg/1.0.0

Supply-Chain Permission Contracts & Sandboxing

To protect host systems from malicious supply-chain attacks, third-party packages must declare what capabilities they require in their bmdpkg.json manifest under the "permissions" object:

network

TCP / UDP / HTTP sockets

filesystem_read

read_file, exists, stat

filesystem_write

write_file, delete_file

subprocess

exec, external processes

✦ Install-Time Supply Chain Warning Notice

Whenever an installed package requests sensitive capabilities (network, filesystem_write, or subprocess), the package installer alerts the developer with a prominent security notice: 

✦ [SECURITY NOTICE] Package requests host permissions: network, subprocess

VM Runtime Sandboxing (OpEnterPackage & OpLeavePackage): During bytecode execution, the VM tracks the active package contract stack. Even if the user executes the host program with --allow-all, an imported package cannot invoke restricted operations unless those permissions were declared in its own bmdpkg.json. Any violation halts execution with a PermissionDenied runtime error.

Compiler Optimization & Verification

AOT Compiler Optimizer & Scientific Benchmarks (-O)

BramandScript includes an Ahead-of-Time (AOT) optimization pass that pre-evaluates constant expressions in the AST (compiler/optimizer.go) and performs peephole opcode compaction. Pass the -O or --optimize flag to run, build, or disasm to activate compile-time optimization:

bash — Optimizing Compiler CLI Flags 
# Run source file with Ahead-of-Time optimizations enabled
bramand run -O app.bmd

# Compile standalone native binary with optimized bytecode
bramand build -O app.bmd -o app_release

# Disassemble optimized bytecode to inspect constant folded opcodes
bramand disasm -O app.bmd

# Execute the comprehensive scientific benchmark suite
bramand run benchmarks/math_benchmarks.bmd
Constant Folding & Instruction Reduction

Expressions like let x = 2 * 3 + 4 * 5 are folded into a single constant 26 at compile time, reducing instruction count and eliminating runtime stack pushes. Consecutive duplicate/pop operations are eliminated during the peephole stage.

Runtime Permission Guards & Configurable Stack

Control execution safety and system resources using explicit runtime flags:

bash — Permission & Stack Options 
# Grant all execution, file system, and network capabilities
bramand run --allow-all app.bmd

# Granular capability grants
bramand run --allow-run script.bmd       # Allow exec()
bramand run --allow-write script.bmd     # Allow write_file(), delete_file()
bramand run --allow-net server.bmd       # Allow tcp_listen()

# Custom call stack depth limit
bramand run --max-frames 2048 deep_recursion.bmd

CLI Runtime Options & Security Flags Reference

Option / FlagDefaultDescription & Protected Operations

--allow-runfalseAuthorizes execution of external subprocesses via exec().
--allow-writefalseAuthorizes file system write and delete mutations (write_file(), append_file(), delete_file()).
--allow-netfalseAuthorizes host network socket listening (tcp_listen(), web servers).

-OfalseEnables ahead-of-time (AOT) constant folding and peephole bytecode optimization.

100% Native BramandScript Tooling Ecosystem (tools/ & std/tooling/)

This architecture ensures that language enhancements immediately benefit the tooling ecosystem while validating the VM's real-world robustness through complete self-hosting and application dogfooding (Rule 11 & Rule 12).
